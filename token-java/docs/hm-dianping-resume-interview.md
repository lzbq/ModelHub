# ModelHub 项目简历总结与面试问答

更新日期：2026-09-22

## 一、项目定位

本项目是一个大模型 API 套餐交易、Token 额度和统一调用平台，覆盖手机号验证码登录、AI 模型目录、Token 套餐、限时抢购、异步订单、模拟支付、额度账户、平台 API Key、真实模型调用和用量记录，并提供 Vue 管理与体验页面。

项目重点不是 CRUD，而是围绕高并发读写、缓存一致性、异步削峰、最终一致性和模型网关计费展开。限时套餐链路使用 Redis Lua、Redis Stream、RocketMQ 和 MySQL；模型网关在服务端保存上游密钥，通过 OpenAI 兼容协议调用百炼等供应商，并按“额度预留 → 上游调用 → 真实 usage 结算或失败释放”处理 Token 额度。

### 项目背景与开发动机

项目设定的业务背景是：AI 应用团队不仅要“调用一个模型”，还要在多个模型之间选型和比较成本，购买 Token 套餐，管理订单与额度，保护 API Key，并在调用异常时完成排查。供应商控制台主要解决模型供给，普通交易系统主要解决购买，两者之间缺少把“套餐额度”和“真实模型消费”连接起来的业务闭环。

我做这个项目的原因，是希望用一个连续场景同时验证三类工程能力：用 Java、Redis 和 RocketMQ 处理高并发套餐交易与最终一致性；用统一网关解决供应商密钥、协议适配、平台鉴权和 usage 结算；用 Python 多 Agent 在最小权限下查询真实模型、套餐、订单和额度数据。最终由 Vue 把“选模型 → 算成本 → 买套餐 → 获得额度 → 创建平台 Key → 调用模型 → 查询 usage → Agent 排障”串起来。

面试短答：

> 我观察到很多大模型 Demo 只完成一次聊天调用，商城 Demo 又停在下单，没有解决模型怎么选、Token 怎么买、实际调用怎么扣额度以及出问题怎么排查。所以我把交易系统、统一模型网关和 Agent 助手组合成一个完整场景。项目价值不在于重复做供应商平台，而在于把高并发交易、真实模型消费和智能售后用统一的身份、额度和业务事实连接起来。

## 二、技术栈

- 后端框架：Spring Boot、Spring MVC、MyBatis-Plus、Lombok。
- 数据存储：MySQL 负责业务主数据和最终订单状态。
- 缓存与高并发：Redis、Lua 脚本、Redis String/Hash/Set/ZSet、Redis Stream。
- 本地缓存：Caffeine，用于热门 AI 模型详情和榜单的 JVM 级缓存加速。
- 消息队列：RocketMQ，用于限时 Token 套餐订单异步创建、订单超时延时处理、AI 模型缓存失效广播。
- 分布式协调：Redisson，用于消费端一人一套餐并发兜底和缓存重建锁。
- 模型网关：OpenAI 兼容的 `/v1/chat/completions`，支持模型别名、平台 API Key、请求限流、幂等、额度预留与真实 usage 结算。
- 前端：Vue 3、TypeScript、Vite，提供模型目录、套餐订单、工作台、API Key 和模型体验页面。
- 工程环境：Java 25、Maven，接口通过 Spring MVC 暴露。

## 四、核心架构说明

### 1. AI 模型缓存查询链路

- 查询模型详情时先查 Caffeine；只有 `hot_score` 达到配置阈值的模型详情才会写入该本地缓存。
- 详情本地缓存未命中后查 Redis；Redis 详情采用空值缓存、随机 TTL 和 Redisson 互斥重建，未使用逻辑过期。
- 查询热门模型榜单时先查 Caffeine，再查带**版本号**的 Redis 逻辑过期缓存；逻辑过期后先返回旧数据，再由后台线程持锁异步刷新。
- 更新 AI 模型时先更新 MySQL，事务提交后清理本机 Caffeine、删除 Redis 模型详情并递增热门榜版本，再发送 RocketMQ 广播，让其他实例清理各自本地缓存。
- 每次成功返回模型详情时记录一次详情访问；订单从待支付成功变为已支付并提交后记录一次购买。模型调用网关已记录真实 usage 和调用流水，但动态热度公式当前仍只使用详情访问与支付购买两个指标。
- 高频事件先聚合在 JVM 的原子计数器中，默认以 `fixedDelay = 1000ms` 逐个活跃“指标类型 + modelId”执行 `ZINCRBY`，写入 `metrics:ai-model:{view|purchase}:{UTC小时}` ZSet；member 为 modelId，score 为该模型在该桶内的累计次数。
- 指标桶默认 TTL 为 72 小时，实际取 `max(metricRetentionHours, 2 × windowHours + 2, 2)`，并在该桶成功写入后尝试重置。默认每小时第 5 分钟由一个节点持 Redisson 锁，读取最近两个 24 小时窗口，应用 12 小时半衰期和增长率公式计算热度分；默认分数上限为 10000。数据库更新提交后批量删除详情缓存、只递增一次榜单版本，并广播各实例清理 Caffeine。

### 2. 限时 Token 套餐秒杀下单链路

- 用户请求秒杀接口后，服务先从 MySQL 联表查询套餐并校验套餐类型、开始时间和结束时间，再生成订单 ID。
- 执行 Redis Lua 脚本，原子判断 Redis 库存、判断用户是否已预占同一套餐、扣减 Redis 库存、记录用户预占资格，并写入 Redis Stream。
- 接口立即返回 orderId，表示抢购资格已获得或下单请求已受理，不等待延时消息。
- 后台线程消费 Redis Stream，并调用 RocketMQ 同步发送；调用未抛异常后 ACK Stream 消息，当前未显式检查 `SendResult.sendStatus`。
- RocketMQ 订单消费者收到消息后，使用 Redisson 按 userId 加锁，然后进入 MySQL 事务创建订单。
- MySQL 创建订单时再次检查订单是否存在、用户是否已有同一套餐的未取消订单，并通过 stock > 0 条件更新扣减真实库存。
- 订单保存为待支付状态后，在事务提交后发送 RocketMQ 延时消息。
- 延时消息到期后，消费者检查订单状态；若仍为待支付，则取消订单、恢复 MySQL 库存并释放 Redis 秒杀库存和用户购买记录；若已支付，则直接忽略。

#### Redis 数据结构与原子预占实现

秒杀链路中的 Redis 不只是普通缓存，而是入口侧的**库存预扣、用户资格和待转发事件状态层**：

| Key | 类型 | 作用 | 写入时机 |
|---|---|---|---|
| `token:stock:{packageId}` | String | 秒杀套餐的 Redis 可用库存 | 调用 `addSeckillPackage` 新增秒杀套餐时，根据 MySQL 初始库存写入 |
| `token:order:{packageId}` | Set | 已预占该套餐的用户 ID，用于一人一套餐 | Lua 预占成功时执行 `SADD` |
| `stream.token.orders` | Stream | 待转发的订单事件，字段为 `userId`、`packageId`、`id` | Lua 预占成功时执行 `XADD` |
| `lock:token-order:{userId}` | Redisson 锁 | 防止同一用户的消息被并发落单 | RocketMQ 订单消费者处理消息时获取 |
| `icr:token-order:{yyyy:MM:dd}` | String 计数器 | 生成订单 ID 的低 32 位日序列 | 每次生成订单 ID 时执行 `INCR` |

主 Lua 在 Redis 中原子执行 `GET 库存 → SISMEMBER 判重 → INCRBY -1 → SADD 用户 → XADD Stream`，返回 `0` 表示预占成功、`1` 表示库存不足、`2` 表示重复预占。补偿 Lua 先执行 `SREM`，只有确实移除了用户资格才执行 `INCRBY +1`，因此重复补偿不会重复增加 Redis 库存。

当前库存 Key、购买资格 Set、Stream 和订单 ID 日计数器都没有 TTL，Stream 消息 ACK 后也没有执行 XDEL 或 XTRIM；SQL 初始化脚本不会自动把 MySQL 库存同步到 Redis，只有服务层的 `addSeckillPackage` 会初始化库存。应用启动时会用 `MKSTREAM` 创建 `token-g1` 消费组，但没有从 MySQL 自动预热库存，也没有定时库存对账。

此外，入口并不是“全部只查 Redis”：每次请求仍会先从 MySQL 联表查询套餐并校验 `type`、`beginTime`、`endTime`，Redis 只承担库存、用户资格和事件中转。极端入口流量下，这次 MySQL 前置查询仍可能成为瓶颈，后续可把活动元数据一并预热到 Redis，并在 Lua 中完成活动状态校验。

### 3. 秒杀链路中的一致性边界

Redis Lua 保证入口资格判断、库存预扣和 Stream 写入的原子性；后台转发器调用 RocketMQ 同步发送且未抛异常后 ACK Stream，但当前未显式检查发送结果状态；RocketMQ 负责订单创建和超时取消的异步解耦；MySQL 通过事务和条件更新保存最终状态。整体目标是最终一致而非强一致，但当前 Pending 消息没有启动恢复或周期扫描，MySQL 事务提交后的延时消息也没有 Outbox 或定时补发，因此故障场景下仍存在消息恢复缺口。

### 4. 订单状态机

- 待支付：用户抢购成功，后台订单已创建，但尚未支付。
- 已支付：用户调用模拟支付接口后，订单从待支付变为已支付，并在同一事务中发放 Token 额度、记录额度流水。
- 已取消：延时消息到期后，订单仍未支付，则取消订单并释放库存。
- 状态更新均使用条件更新，例如只有 status = 待支付 时才能支付或取消，避免支付和超时取消并发造成状态错乱。

### 5. 模型调用网关与额度结算

- 对客户端提供 OpenAI 兼容的 `/v1/chat/completions` 和前端专用 `/gateway/chat/completions`；模型别名映射到数据库模型 ID 与供应商模型 ID，避免客户端依赖上游命名。
- 登录页面调用使用会话 Token，外部应用使用只展示一次明文的 `mh_` 平台 API Key；上游供应商 Key 仅从服务端环境变量或被 Git 忽略的 `.env` 读取。
- 请求进入后校验模型、正文大小、`max_tokens`、每分钟请求数和幂等键，再按请求上限预留套餐额度。
- 上游成功时读取真实 `usage`，把预留额度调整为实际消耗并保存调用流水；明确的 4xx/5xx 拒绝会释放预留，结果不确定的异常保留待核对状态，避免既重复扣费又静默放行。
- 当前已经用阿里云百炼北京业务空间的 OpenAI 兼容地址完成真实调用验证，供应商模型 ID 使用区分大小写的 `qwen3.5-flash`。
- Vue 前端通过 Vite 代理访问 Java 与 Python 服务，覆盖模型体验、调用记录、额度、套餐订单和平台 API Key 管理。

## 六、3 分钟项目介绍

这个项目是一个大模型 API 套餐交易、Token 额度和统一调用平台，业务上分为用户、模型目录、Token 套餐、订单、额度账户、平台密钥和模型网关几个模块。基础功能包括手机号验证码登录、模型热门榜与搜索、套餐购买、限时抢购、模拟支付、额度发放、真实上游调用和调用记录查询。

技术重点主要有两块。第一块是 AI 模型缓存。模型详情先查 Caffeine，再查 Redis，最后回源 MySQL；Redis 详情通过空值缓存、随机 TTL 和 Redisson 互斥重建处理穿透、雪崩和击穿。热门榜单使用 Caffeine + Redis 逻辑过期，过期后先返回旧值再异步刷新。模型更新时先更新数据库，事务提交后清理本机 Caffeine、删除 Redis 详情、递增榜单版本，并用 RocketMQ 广播通知其他实例清理本地缓存。

第二块是限时套餐订单。我把库存和一人一套餐资格判断放在 Redis 层，用 Lua 脚本保证判断、扣减 Redis 库存和写入 Stream 是一个原子操作。后台线程从 Redis Stream 读取消息并发送到 RocketMQ，RocketMQ 消费者负责创建 MySQL 订单。创建订单时还会做幂等判断、Redisson 用户维度加锁和 MySQL 条件扣库存，防止重复消费或并发消费导致重复下单。订单创建后发送 RocketMQ 延时消息，到期检查订单状态，未支付就取消订单并恢复库存，已支付则忽略；模拟支付成功时还会在事务中发放 Token 额度。这个设计的目标是让 Redis 承接高并发资格判断，RocketMQ 解耦订单处理，MySQL 只承接通过 Redis 资格校验的订单写入并保存最终状态。

第三块是模型网关。我在 Java 服务里实现 OpenAI 兼容接口，用模型别名隔离供应商差异，用平台 API Key 或登录会话识别调用者，并加入请求限流、幂等和输入输出限制。调用前按最大输出预留模型账户额度，上游成功后根据真实 usage 结算并释放剩余预留，明确失败则回滚预留；每次调用都会形成可查询的状态和成本记录。供应商密钥保留在服务端 `.env`，不会下发到浏览器。

## 七、面试高频问题与回答

### Q1：这个项目最核心的难点是什么？

回答：核心难点是**限时 Token 套餐下单和缓存一致性**。秒杀下单要解决高并发下库存不超卖、一人一套餐、异步订单中转、重复消息幂等、超时未支付释放库存。缓存一致性要解决 AI 模型更新后 Redis 和多实例 Caffeine 本地缓存的失效问题。

### Q2：为什么秒杀入口不用 MySQL 直接扣库存？

回答：秒杀请求量通常远大于真实库存，如果在 MySQL 直接扣库存并同步创建订单，会造成行锁竞争和数据库压力。当前实现仍会在 Lua 前查询 MySQL，校验套餐类型和活动时间；库存与一人一套餐资格判断则前置到 Redis，只把通过资格校验的订单异步写入 MySQL。

### Q3：秒杀链路的 Redis 状态和 Lua 原子预占是怎么实现的？

回答：项目使用三个核心 Redis 数据结构：String `token:stock:{packageId}` 保存预扣库存，Set `token:order:{packageId}` 保存已预占用户，Stream `stream.token.orders` 保存待转发订单事件。主 Lua 原子执行库存读取、库存不足判断、用户重复预占判断、库存减一、记录用户资格和写入 Stream，返回 `0/1/2` 分别代表成功、库存不足、重复预占。这样可以避免“判断有库存后被其他请求抢先扣减”以及“库存已扣但 JVM 在写消息前宕机”的窗口。

取消订单或 MySQL 扣库存失败时会调用释放 Lua：只有 `SREM` 确实移除用户资格，才把 Redis 库存加一，因此重复执行补偿不会重复加库存。Lua 的原子性只覆盖 Redis，不等于 MySQL、Redis、RocketMQ 的分布式事务。当前主脚本通过 ARGV 拼业务 Key，更适合单机 Redis；如果部署 Redis Cluster，应改为显式传入 `KEYS`，并用统一 Hash Tag 保证相关 Key 落在同一槽位。

### Q4：一人一套餐是怎么保证的？

回答：第一层是 **Lua** 中用 Redis Set 判断用户是否已有该 Token 套餐的有效预占资格。第二层是 **RocketMQ 消费端**用 Redisson 按 userId 加锁，防止重复消息并发创建订单。第三层是 **MySQL** 创建订单前查询该用户是否已有同一套餐的未取消订单；若存在，则补偿 Redis 后结束消费。

### Q5：Redisson 锁是否还能删？

回答：当前不宜直接删除。RocketMQ 可能重复投递，也可能有多个消费者并发处理同一用户消息；而当前订单表的 `(user_id, package_id)` 只是普通索引，不是唯一约束。Redisson 用户锁配合订单 ID 和用户/套餐查询，是消费端的并发兜底；只有补齐可靠的数据库唯一性或等价幂等设计后，才适合重新评估是否删除。

### Q6：项目里有没有使用乐观锁？

回答：项目中有两类乐观并发控制。秒杀库存通过 `stock > 0` 条件更新避免库存扣成负数，但它不是传统的 version 字段乐观锁；Token 额度账户更新则显式校验 `version` 并在成功后加一，防止并发发放相互覆盖。

### Q7：Redis 库存已经扣了，MySQL 扣库存失败怎么办？

回答：当前消费者创建订单时，如果 MySQL 条件扣减返回失败，会移除用户购买资格、恢复 Redis 库存后正常结束消费，不创建订单；如果处理过程直接抛异常，则由 RocketMQ 的消费失败机制重投。项目尚未实现死信监听和定时对账，生产环境还需要补齐告警与补偿。

### Q8：为什么 Lua 成功后还要 Redis Stream？

回答：因为 Lua 成功意味着 Redis 库存和用户资格已经改变。如果 Lua 返回后应用还没来得及发送 RocketMQ 就宕机，会出现 Redis 已扣库存但 MQ 没消息、MySQL 没订单。把 Stream 写入放进同一个 Lua，可以原子留下待转发事件；未被读取的新消息可在应用恢复后继续消费。但当前实现没有在启动时或周期性恢复已读未 ACK 的 Pending 消息，这部分仍需完善。

### Q9：只用 Redis Stream 不用 RocketMQ 可以吗？

回答：可以，Redis Stream 本身能做消息队列，也支持消费者组和 Pending List。但 RocketMQ 在消息重试、延时消息、消费组治理、死信队列、服务解耦和运维观测上更适合业务消息。当前项目让 Stream 做入口中转，让 RocketMQ 做订单处理和超时取消。

### Q10：不用 Stream，Lua 成功后直接发 RocketMQ 会怎样？

回答：代码会更简单，但有一致性缺口：Lua 已经扣 Redis 库存和记录用户资格，应用在发送 RocketMQ 前宕机，订单消息会丢失。之后用户不能再次抢，MySQL 又没有订单，需要额外补偿机制修复。 

### Q11：能不能用 RocketMQ 事务消息替代 Redis Stream？

回答：可以设计为先发半消息，再执行 Redis Lua，Lua 成功则提交事务消息，失败则回滚。同时需要持久化可供 Broker 事务回查的业务状态并实现事务状态检查，否则生产者在 Lua 成功后、提交事务消息前宕机时，仍无法可靠判定提交或回滚。该方案还会让 RocketMQ 进入秒杀入口热路径，库存不足和重复下单请求也会先打到 MQ，削弱 Redis 前置削峰的优势。

### Q12：RocketMQ 在项目中承担什么职责？

回答：三个职责：第一，限时 Token 套餐订单创建异步化，把 Redis 入口和 MySQL 落库解耦；第二，延时消息处理超时未支付订单；第三，AI 模型更新后广播缓存失效消息，通知多实例清理本地缓存。

### Q13：RocketMQ 消息重复消费怎么办？

回答：消费者要做幂等。**订单创建消费者**先按 userId 获取 Redisson 锁，进入事务后根据 orderId 判断订单是否已存在，再判断该用户是否已有同一套餐的未取消订单。**超时取消消费者**只处理待支付订单，已支付或已取消订单直接忽略。

### Q14：延时消息到了，用户刚好支付怎么办？

回答：**支付和取消都使用条件更新**。支付只允许 status = 待支付 更新为已支付；取消只允许 status = 待支付 更新为已取消。谁先更新成功，另一个操作就会失败或被忽略，从而避免状态错乱。

### Q15：为什么订单创建成功后要 afterCommit 再发送延时消息？

回答：如果在事务提交前发送延时消息，可能出现数据库事务回滚但消息已经发出的情况。afterCommit 能保证先持久化订单再发送超时检查消息，降低“事务回滚但消息已发出”的风险；但提交后发送仍有失败窗口，当前没有 Outbox 或超时订单扫描，不能把它表述为完整的可靠投递保证。

### Q16：延时消息是不是让用户等到超时时间才知道购买成功？

回答：不是。延时消息只负责超时取消。用户抢购成功后接口应立即返回 orderId，表示抢购资格或下单请求受理。订单创建后是待支付状态，用户支付成功后才是购买成功。延时消息到期只检查是否需要取消。

### Q17：当前项目的最终一致性是如何体现的？

回答：秒杀入口先更新 Redis 状态，订单再异步写 MySQL；如果 MySQL 条件扣库存失败，则补偿 Redis 后结束消费，订单超时后再按状态补偿 MySQL 和 Redis 库存。正常消息链路下通过幂等、状态检查和超时补偿趋向最终一致，但当前仍缺少 Pending 启动/周期恢复、事务提交后消息的可靠补发和定时对账，因此不能无条件宣称所有故障场景都能最终一致。

### Q18：AI 模型详情缓存如何解决缓存穿透？

回答：项目会缓存空值。查询不存在的模型时，向 Redis 写入带短 TTL 和随机抖动的空字符串，后续相同请求直接返回，避免反复穿透到 MySQL。

### Q19：AI 模型缓存如何解决缓存击穿？

回答：模型详情在 Redis 未命中时使用 Redisson 互斥锁和 Double Check，由持锁线程回源并回填；未取得锁的线程等待后会再读 Redis，仍未命中时降级查 MySQL 但不回填。热门模型榜单使用逻辑过期，过期后先返回旧数据，再由后台线程持锁异步刷新。两条查询链路的策略不同。

### Q20：AI 模型缓存如何解决缓存雪崩？

回答：模型详情的正常值和空值 TTL 都加入随机扰动，避免大量 Key 同时过期；热门榜单的逻辑过期时间也带随机值，并保留更长的物理 TTL。缓存预热、限流和降级目前尚未实现。

### Q21：为什么引入 Caffeine 本地缓存？

回答：热门 AI 模型详情和榜单是读多写少场景，频繁访问时每次都查 Redis 仍有网络开销。Caffeine 放在 JVM 内存中，可以减少 Redis 压力；详情只有 `hot_score` 达到阈值时才写入本地缓存，热门榜单则按分类和页码缓存。本地缓存存在多实例一致性问题，所以更新时需要广播失效。

### Q22：Caffeine + Redis 缓存怎么删除，删除过程中有并发访问会怎样？

回答：更新 AI 模型时先更新 MySQL，事务提交后依次清理当前实例 Caffeine、删除 Redis 模型详情、递增热门榜版本号，再通过 RocketMQ 广播 modelId，让其他实例清理各自的 Caffeine。榜单旧版本 Key 不立即删除，而是因为版本切换不再被新请求读取，最终由 10 分钟物理 TTL 淘汰。

并发删除期间不是强一致：失效前或广播到达前，请求可能命中旧 Caffeine；共享 Redis 删除后，第一个未命中请求会通过 Redisson 锁从已提交的 MySQL 重建缓存，未拿到锁的请求重读 Redis，仍未命中则直接查数据库但不回填。还存在理论上的在途请求竞争，例如某请求先读到旧数据库数据、随后跨过缓存删除再写回旧 JSON。当前详情缓存没有版本号、延迟双删或写入 CAS，这种极端情况下旧 Redis 详情可能持续到 10～15 分钟 TTL 到期；旧本地详情和榜单分别由 1 分钟、15 秒 TTL 兜底。直接执行 SQL 修改数据库也不会触发上述失效流程。

### Q23：为什么 AI 模型缓存失效用 RocketMQ 广播模式？

回答：因为每个应用实例都有自己的本地 Caffeine 缓存。普通集群消费只会让一个实例收到消息，而广播模式可以让所有实例都收到失效通知，从而清理各自本地缓存。

### Q24：热门模型如何判定，`hot_score` 如何设计，是否自动识别？

回答：当前已经实现基于近期行为的动态热度计算。`hot_score` 最终持久化在 MySQL 的 `tb_ai_model` 中，默认取值为 0～10000（上限可配置），同时承担两个职责：

- 热门详情准入：`hotScore >= hotScoreThreshold` 时，模型详情才进入 Caffeine；默认阈值为 8000，可通过 `AI_MODEL_HOT_SCORE_THRESHOLD` 修改。
- 热门榜排序：所有 `status = 1` 的模型都参与榜单，按 `hot_score DESC` 分页；榜单本身不应用 8000 分门槛。

#### 1. 完整处理流程

```text
详情访问 / 订单支付成功
  → JVM 按“指标类型 + modelId”内存聚合
  → 默认 fixedDelay 1000ms，逐个活跃项 ZINCRBY 到 Redis 小时 ZSet
  → 每小时第 5 分钟获取 Redisson 分布式锁
  → 读取最近 24 个完整小时和前 24 个小时
  → 时间衰减、对数归一化、业务权重、增长率计算
  → 在 MySQL 事务中逐模型更新发生变化的 hot_score
  → 事务提交后批量删除详情缓存并切换一次榜单版本
  → RocketMQ 广播其他实例清理 Caffeine
```

#### 2. 两类指标从哪里产生

| 指标 | 记录时机 | 说明 |
|---|---|---|
| 详情访问量 `view` | `GET /ai-model/{id}` 成功返回时 | 无论命中 Caffeine、Redis 还是 MySQL，只要详情成功返回就记录一次；查询不存在或已下架模型不统计 |
| 购买量 `purchase` | 订单由待支付成功变为已支付，且事务提交后 | 重复支付不会重复记录；事务回滚也不会产生购买指标 |

项目已经有服务端模型调用网关，可以产生可信的供应商调用结果和 usage 流水；但动态热度计算目前仍只消费详情访问与支付购买指标，还没有把网关成功调用接入热度公式。后续应直接使用服务端调用流水聚合事件，不恢复面向普通用户的“调用成功”上报接口。

#### 3. 为什么先在 JVM 内聚合

如果每次详情访问都立即执行 Redis `ZINCRBY`，即使命中了 Caffeine，也会重新产生一次 Redis 网络调用，削弱本地缓存的意义。因此项目使用如下内存结构累计事件：

```text
EnumMap<MetricType, ConcurrentHashMap<modelId, AtomicLong>>
```

每次事件只执行本地原子自增；`flushMetrics` 使用 `fixedDelay`，默认在上一次刷盘结束 1000ms 后再次执行。一次刷盘会合并同模型、同指标的本地次数，但仍会对每个活跃的“指标类型 + modelId”分别执行一次 `ZINCRBY`，当前没有使用 Pipeline 或单条 Redis 批量命令。

写入前通过 `getAndSet(0)` 取走本地计数；Redis 抛异常时会把次数加回本地等待下次重试。不过它不提供 exactly-once 语义：Redis 长时间不可用后若 JVM 崩溃，可能丢失超过 1 秒的未落盘累计量；如果 Redis 已执行 `ZINCRBY` 但客户端没有收到响应，异常重试还可能重复累计。

#### 4. Redis 存储结构

动态热度指标使用两个按 UTC 小时分桶的 ZSet：

| Redis Key | 类型 | Member | Score | 默认 TTL |
|---|---|---|---|---|
| `metrics:ai-model:view:{yyyyMMddHH}` | ZSet | modelId 字符串 | 该模型本小时详情访问次数 | 72 小时 |
| `metrics:ai-model:purchase:{yyyyMMddHH}` | ZSet | modelId 字符串 | 该模型本小时支付购买次数 | 72 小时 |

例如模型 3 在 UTC `2026091114` 这一小时新增 25 次详情访问：

```redis
ZINCRBY metrics:ai-model:view:2026091114 25 3
```

对应的逻辑结构可以理解为：

```text
metrics:ai-model:view:2026091114
  member "1" → score 152
  member "2" → score 87
  member "3" → score 241
```

TTL 为 `max(metricRetentionHours, 2 × windowHours + 2, 2)` 小时，保证“近期窗口 + 对照窗口”都没有过期，并在该桶成功写入后尝试重置；如果单独设置 TTL 失败，本次指标已经落盘，后续再次写该桶时会重试。默认窗口为 24 小时，因此窗口要求的下限是 50 小时，配置默认值为 72 小时。

小时桶按**刷盘时刻**归属，而不是为每条事件保存发生时间。由于内存计数器不记录事件时间戳，临近整点的少量事件可能在下一次刷盘时进入下一个 UTC 小时桶；Redis 故障导致计数积压时，偏移还可能更大。

需要区分两种 Redis 数据：

- 上述 `metrics:ai-model:*` ZSet 是热度计算的原始小时指标。
- 对外热门榜缓存仍然是 `cache:ai-model:hot:{version}:{category}:{pageNo}` String，Value 为 `{"data":[...],"expireAt":...}`，并不是直接拿指标 ZSet 当排行榜。

#### 5. 时间窗口与定时调度

`flushMetrics` 默认每秒运行，各应用实例都会把自己的本地计数写入共享 Redis。`refreshScores` 默认使用 Cron `0 5 * * * *`，即每小时第 5 分钟执行。

多实例会竞争 `lock:ai-model:hot-score:refresh` Redisson 锁，只有一个实例负责本轮计算。计算时不读取尚未结束的当前小时，而是读取：

- offset 1～24：最近 24 个完整小时，作为**近期窗口**。
- offset 25～48：再往前 24 个小时，作为**对照窗口**。

因此一次新行为进入数据库 `hot_score` 的延迟约为 5～65 分钟。只有全局两个窗口都没有任何有效指标时，任务才整体跳过并保留原分数，避免系统刚部署时把初始化分数全部更新为 0。只要任一模型存在窗口指标，任务就会遍历 `tb_ai_model` 全表，包括下架模型；某个模型在两个窗口都没有指标时会直接计算为 0，而有历史指标的模型会随时间衰减并最终降到 0。

#### 6. 时间衰减与数量归一化

每个窗口内的小时数据先按 12 小时半衰期衰减：

```text
ageInsideWindow = ((offset - 1) % windowHours) + 0.5
decay(ageInsideWindow) = 0.5 ^ (ageInsideWindow / halfLifeHours)
decayedCount = Σ(hourCount × decay)
```

默认 24 小时窗口中，近期窗口和对照窗口都分别使用 `0.5、1.5、...、23.5` 小时作为桶的相对年龄。也就是说，对照窗口会独立重置衰减年龄，并不会按其距离当前时间的实际 `24.5～47.5` 小时再次额外衰减；这样是在比较两个窗口内相同位置的活跃度。约 12 小时相对年龄的数据保留一半权重，约 24 小时相对年龄的数据保留四分之一权重。

衰减后的数量再使用对数归一化，避免少数绝对流量很大的模型长期垄断分数：

```text
signal = min(1, log1p(decayedCount) / log1p(saturation))
```

默认饱和值为：详情访问量 5000、购买量 100。达到饱和值后该项等于 1，继续增加流量不会再提高该项信号。

#### 7. 权重和增长率公式

近期基础活跃度：

```text
recentActivity =
    0.35 × viewSignal
  + 0.50 × purchaseSignal
```

对照窗口使用同一套衰减、归一化和权重得到 `previousActivity`，再计算增长信号：

```text
growthRate   = (recentActivity - previousActivity) / previousActivity
growthSignal = clamp(growthRate / maxGrowthRate, -1, 1)
```

特殊情况：两个窗口都为 0 时增长信号为 0；对照窗口为 0、近期窗口大于 0 时增长信号直接取 1。`maxGrowthRate` 默认为 3，表示增长率达到 `+300%` 时增长信号封顶，即 `recentActivity = 4 × previousActivity` 时取 1。

通用最终公式中，访问和购买权重会先截断为非负数，分母使用全部权重的非负部分。当前源码在增长项分子中直接使用 `growthWeight`，因此生产配置应保持所有权重非负：

```text
base = max(0, detailViewWeight) × viewSignal
     + max(0, purchaseWeight) × purchaseSignal

totalWeight = max(0, detailViewWeight)
            + max(0, purchaseWeight)
            + max(0, growthWeight)

weightedScore = base + growthWeight × growthSignal

hotScore = round(
    maxScore × clamp(
        weightedScore / totalWeight,
        0, 1
    )
)
```

若 `totalWeight = 0`，分数直接返回 0。默认三项权重之和正好为 1，因此可简化为：

```text
hotScore = round(
    10000 × clamp(
        0.35 × viewSignal
      + 0.50 × purchaseSignal
      + 0.15 × growthSignal,
        0, 1
    )
)
```

访问、购买和增长率权重分别为 35%、50%、15%。购买是完成支付后的可信商业行为，因此权重最高；详情访问反映关注度但更容易被刷，权重低于购买；增长率用于发现短时间快速上升的新模型。所有权重、窗口、半衰期、饱和值、最大增长率、总分上限和刷新时间都可以通过 `modelhub.hot-score` 配置。

#### 8. 数据库更新与缓存联动

定时任务读取全部模型当前分数，没有按 `status` 过滤；随后在同一 MySQL 事务中遍历模型，对每个分数发生变化的模型执行一条 `UPDATE`，并不是一条批量更新 SQL。事务提交后再执行：

1. 批量清除变化模型的本机 Caffeine 详情。
2. 清空本机热门榜 Caffeine。
3. 批量删除 `cache:ai-model:{modelId}` Redis 详情。
4. `INCR cache:ai-model:hot:version`，整批更新只切换一次榜单版本。
5. 逐模型发送 RocketMQ 广播，让其他实例清理本地 Caffeine。

下一次详情或榜单请求会回源并读取新的分数。管理员仍可通过更新模型接口提交 `hotScore`，但只要存在非空的动态指标窗口，下一次定时计算就会用行为分覆盖它；初始化 SQL 只提供首次建库种子分，重复执行时不会覆盖动态结果。

#### 9. 当前边界

- 动态计算不等于实时更新，默认按完整小时窗口计算。
- JVM 聚合降低 Redis 压力，但不保证 exactly-once：进程崩溃会丢失尚未落盘的本机累计量，响应不确定的 Redis 写重试可能造成重复计数。
- 详情接口公开，访问量在生产环境仍需增加防刷和异常流量过滤；购买指标来自支付成功后的服务端事务，可信度更高。
- 当前实现动态计算分数并驱动 Caffeine 准入，但尚未根据 TopN 主动预热缓存。

### Q25：登录为什么用 Redis 存 Token？

回答：服务端生成随机 Token，把用户简要信息存到 Redis Hash，并设置过期时间。这样避免 Session 依赖单机内存，支持分布式部署；拦截器每次请求校验 Token 并刷新 TTL。

### Q26：Redis 全局 ID 怎么设计？

回答：当前实现使用**相对时间戳**作为高 32 位，并将 **Redis 按日期维护的自增序列**放在低 32 位。时间戳保证整体趋势递增，日序列保证同一时间片内唯一，生成订单 ID 时不依赖数据库自增。

### Q27：为什么不用 RabbitMQ？

回答：RabbitMQ 也能实现异步下单和延时处理，比如 **延迟队列（TTL + 死信交换机）**。但 RocketMQ 原生支持更丰富的业务消息能力，例如**延时消息、事务消息、重试队列和死信队列**，在订单状态流转和最终一致性场景中表达更直接。项目选择 RocketMQ 是为了贴合**订单创建、超时取消和服务解耦**场景。

### Q28：项目有哪些可以继续优化的地方？

回答：可以补充 Stream Pending 的启动恢复、周期扫描/claim 和实例唯一消费者名，增加 MQ 死信队列告警、Outbox 或定时对账、订单业务幂等约束、热点 Key 动态识别、接口限流、库存预热管理后台、真实支付回调幂等、链路追踪和压测报告。

### Q29：如果 RocketMQ 挂了会怎样？

回答：订单消息同步发送调用抛异常时，Stream 记录不会被 ACK，当前线程会立即尝试处理 Pending；但再次失败后会退出 Pending 处理，项目没有启动恢复或周期扫描，因此 MQ 恢复后旧 Pending 不保证自动重发。当前也没有显式检查同步发送返回的非 `SEND_OK` 状态。若订单事务已提交但延时消息发送失败，当前没有 Outbox 或超时订单扫描；缓存广播失败时，其他实例只能等待本地 Caffeine 到期。生产环境应补充 MQ 高可用、发送结果校验、Pending 恢复、可靠消息补发、死信告警和定时对账。

当前项目对 RocketMQ 的依赖比较脆弱：订单链路 Pending 不保证恢复、超时链路没有兜底补偿、缓存广播失败只能等 TTL。生产环境至少要补三件事——发送结果校验、Pending 周期扫描恢复、以及超时订单的定时对账兜底。长期来看，建议用 Redis 原生能力（Stream 直接消费、ZSet 延迟队列、Pub/Sub 广播）替代 RocketMQ，减少外部依赖，从根本上提升可靠性。

### Q30：如果 Redis 挂了会怎样？

回答：Redis 不可用时，登录、秒杀、AI 模型详情/热门榜等 Redis 依赖路径会失败；不带登录 Token 的 AI 模型关键词搜索和 Token 套餐查询仍可直接访问 MySQL，已命中 Caffeine 的详情或榜单也可返回。上述 Redis 依赖路径目前没有降级回源。生产环境应快速失败或熔断，不能把秒杀流量直接放到 MySQL，并应配置 Redis 高可用、监控和限流。

### Q31：项目有没有实测出超卖，代码如何防止，怎么验证？

回答：仓库里没有秒杀并发测试、JMeter 脚本、JTL 结果或线上监控数据，所以不能声称“已经实测没有超卖”，也没有证据表明曾经发生过超卖。正常链路设计了两层库存防线：入口层 Redis Lua 原子检查并预扣库存，落库层 MySQL 执行 `stock = stock - 1 WHERE package_id = ? AND stock > 0`，只有扣减成功才创建订单，因此数据库库存不会在正常事务链路中被扣成负数。

重复购买方面还有 Redis Set、消费端 userId 维度 Redisson 锁、orderId 幂等检查和用户/套餐未取消订单查询；取消时通过状态条件更新和幂等释放 Lua 恢复库存。但订单表的 `(user_id, package_id)` 目前只是普通索引而非唯一约束，所以“一人一套餐”没有数据库最终约束。Lua 返回成功也只表示 Redis 资格预占成功，不代表 MySQL 订单已经落库；消息故障更可能造成库存冻结或少卖，也必须通过对账发现。

验证时应准备初始库存 `S0`，使用大于 `S0` 的不同登录用户并发请求，暂停或延长超时取消，等待 Stream、RocketMQ 和数据库消费完毕，再断言：MySQL/Redis 库存均不小于 0、有效订单数不超过 `S0`、`MySQL 剩余库存 + 未取消订单数 = S0`、同一用户没有两条未取消订单，并且每个 Lua 成功的 orderId 最终都已落库或有明确补偿记录。

### Q32：项目 RocketMQ 如何进行幂等判断、失败重试和异步解耦？

回答：幂等方面，入口用 Redis Set 防止同一用户重复预占同一套餐；订单消费者按 userId 加锁，进入事务后根据 orderId 判断订单是否已存在，再判断该用户是否已有同一套餐的未取消订单；超时消费者只处理待支付订单；AI 模型缓存失效消息重复执行仍只是清理缓存。订单表目前没有用户/套餐唯一约束。

失败重试方面，Stream 转发调用 RocketMQ 同步发送且未抛异常后 ACK（当前没有显式检查发送结果状态）；抛异常时会进入一次 Pending 处理（但没有启动恢复或周期扫描）。订单和超时消费者抛异常时依赖 RocketMQ Spring 的失败重投（项目未配置自定义死信监听）。

异步解耦方面，秒杀请求先写 Redis/Stream，订单落库和超时处理交给 RocketMQ 消费者。

### Q33：AI 模型详情在 Redis 中是如何存储的？

回答：**详情 Redis Key 是 `cache:ai-model:{modelId}`，数据类型为 String，Value 是完整 `AiModel` 对象序列化后的 JSON**，包含厂商、名称、分类、描述、上下文窗口、输入/输出价格、状态、热度值和时间字段。正常值基础 TTL 为 10 分钟，再增加 0～5 分钟随机抖动；数据库不存在时写入空字符串，TTL 为 2～4 分钟，用来防止缓存穿透。

查询顺序是 Caffeine → Redis → MySQL。Redis 未命中时使用 `lock:cache:ai-model:{modelId}` Redisson 锁和 Double Check 重建缓存，抢不到锁的请求重读 Redis，仍未命中则降级查 MySQL，但不写缓存。只有上架且热度达到阈值的详情会放入 Caffeine，本地详情最多 1000 条，写入后 1 分钟过期。

### Q34：AI 模型榜单如何设计，在 Redis 中如何存储？

回答：数据库只查询 `status = 1` 的模型，可按 category 精确过滤，然后按 `hot_score DESC` 排序，每页 10 条。**Caffeine 的 Key 是 `{category 或 all}:{pageNo}`，Value 是 `List<AiModel>`**，最多 500 条，写入后 15 秒过期。

Redis 榜单不是 ZSet，而是版本化 String：版本号保存在 `cache:ai-model:hot:version`，具体榜单 Key 为 `cache:ai-model:hot:{version}:{category}:{pageNo}`，**Value 结构为 `{"data":[],"expireAt":毫秒时间戳}`**。逻辑 TTL 为 60～90 秒，Redis 物理 TTL 为 10 分钟。Key 不存在时持 Redisson 锁同步回源；逻辑过期时先返回旧榜单，再由后台线程异步刷新，从而避免热点榜单同时失效时大量请求阻塞数据库。

### Q35：Redis 缓存什么时候写入，模型详情什么时候更新？

回答：**AI 模型缓存**采用懒加载，没有启动预热。详情在第一次查询或缓存过期后的请求获得重建锁时写入 Redis；榜单在某个版本、分类和页码第一次访问时同步写入，逻辑过期后由后续访问触发异步刷新。非空关键词搜索直接查 MySQL，不进入这套缓存。

数据库模型信息通过 `PUT /admin/ai-model` 调用 `updateById` 更新。事务提交后只做缓存失效和榜单版本切换，不主动把新数据写回缓存，下一次访问再从 MySQL 懒加载。直接修改数据库不会触发缓存失效。**秒杀库存**则不同：只有调用服务层 `addSeckillPackage` 新增秒杀套餐时才写入 `token:stock:{packageId}`；目前没有应用启动时从 MySQL 自动恢复库存的逻辑。

`hot_score` 还会被动态热度任务定时更新：默认每小时第 5 分钟读取 Redis 近期指标，并在事务内逐模型更新分数发生变化的记录；提交后统一失效详情缓存、切换一次榜单版本，再通过 RocketMQ 广播清理其他实例 Caffeine。初始化 SQL 只为首次建库提供种子分，重复执行时不再覆盖已经动态计算出的热度分；只要存在非空的动态指标窗口，管理员手工提交的 `hotScore` 也会在下一次定时计算时被行为分覆盖。

### Q36：数据库怎么设计，一共有多少张表？

回答：初始化脚本创建 7 张 InnoDB 表，关联关系由应用维护，没有声明外键：

| 表名 | 职责和关键约束 |
|---|---|
| `tb_user` | 用户主表，手机号唯一 |
| `tb_ai_model` | 模型目录、价格、状态、热度；索引为 `(category, hot_score)` |
| `tb_token_package` | 套餐公共商品信息；索引为 `(model_id, status)` |

| `tb_token_order` | 订单和额度快照，`id` 由 Redis 全局 ID 生成器提供；用户/套餐索引不唯一 |
| `tb_token_account` | 用户按模型聚合的 Token 账户，`(user_id, model_id)` 唯一，并使用 version 乐观锁 |

逻辑关系可以概括为：模型 1:N 套餐，套餐 1:0..1 秒杀扩展，用户 1:N 订单，用户和模型 1:1 额度账户，订单 1:0..1 额度发放流水。

### Q37：套餐表和秒杀套餐表为什么分开设计？

回答：`tb_token_package` 保存模型、标题、Token 数量、价格、有效期、类型和状态等所有套餐共有且相对稳定的商品信息；`tb_seckill_token_package` 只保存秒杀才需要且更新频繁的库存、开始时间、结束时间。两表通过 `package_id` 形成 1:0..1 扩展关系，查询时用 LEFT JOIN 组装完整套餐。

这样可以避免普通套餐出现无意义的库存和活动时间字段，并把高竞争库存行与商品元数据隔离，减少更新库存时对公共商品数据的影响。代价是需要维护基础表、秒杀扩展表和 Redis 库存的一致性。当前没有外键或检查约束，MySQL 的两次写受本地事务保护，但 Redis 库存初始化不属于 MySQL 事务，跨库并不是原子的。

### Q38：模型缓存、秒杀和 RocketMQ 削峰能力应该如何压测？

回答：当前没有可引用的 QPS、响应时间、请求成功率或 RocketMQ 削峰测试结果，不能根据代码直接估算数字。压测前应固定应用实例数、CPU/内存、JVM 参数、MySQL/Redis/RocketMQ 部署、连接池、数据量和网络环境，并进行预热；报告至少给出吞吐量、P50/P95/P99、错误率、资源使用率和测试持续时间。

**模型详情和榜单缓存测试：**分别测试 Caffeine 命中、仅 Redis 命中、Redis 与 Caffeine 都未命中三种场景，接口使用 `GET /ai-model/{id}` 和 `GET /ai-model/hot?category=chat&current=1`。通过阶梯加压寻找满足目标 P99 和错误率时的最大稳定 QPS，同时观察 Caffeine/Redis 命中率、Redis Ops、MySQL QPS、连接池等待和数据库慢查询。冷缓存测试前必须确认本机 Caffeine 也已清空，不能只删除 Redis Key。

**秒杀测试：**准备 `U > S0` 个不同用户 Token 和初始库存 `S0`，每个用户只请求一次 `POST /token-order/seckill/{packageId}`；测试期间延长订单超时，避免自动取消干扰结果。区分 HTTP 成功率、Lua 预占率和最终落单率：`HTTP 2xx / 总请求`、`Lua 返回 0 / 总请求`、`最终订单数 / Lua 成功数`。接口返回 orderId 只能计为“受理成功”，不能计为最终订单成功。

**RocketMQ 异步削峰测试：**同时记录入口请求 QPS、Redis Stream XADD 速率、Stream Pending/积压、RocketMQ 生产 TPS、Broker 队列积压、消费者 TPS、MySQL 订单写入 TPS 和积压清空耗时。可以限制或暂停订单消费者制造积压，再恢复消费者，验证入口峰值由 Redis 承接、数据库写入被平滑到消费者稳定吞吐。这里应分别报告“入口峰值 QPS”“稳定消费 TPS”“最大积压量”和“恢复耗时”，不能用一个所谓“MQ 削峰 QPS”概括全部能力。

压测结束后还必须执行库存和订单对账，并检查 `GET token:stock:{packageId}`、`SCARD token:order:{packageId}`、`XINFO GROUPS stream.token.orders`、`XPENDING stream.token.orders token-g1`，否则只能证明接口扛住了流量，不能证明消息最终处理成功或没有超卖。

### Q40：模型网关如何避免超扣、重复扣费和供应商密钥泄露？

回答：供应商 API Key 只保存在服务端环境变量或被 Git 忽略的 `.env`，浏览器拿到的是平台会话或 `mh_` 平台密钥。请求进入后先做身份、模型、限流和幂等校验，再以模型账户为粒度预留本次最大可消费额度。上游成功后读取供应商返回的真实 usage，用“实际消耗替换预留”；上游明确拒绝时释放预留；网络超时等结果不确定场景保留待核对状态，交给后续对账处理。相同幂等键不会再次发起和重复结算同一请求。

### Q41：这个项目的背景是什么，为什么要做这个项目？

回答：项目面向需要统一采购和使用大模型能力的开发者与 AI 应用团队。实际流程不只是发送一次模型请求，还包括模型选型、成本估算、套餐购买、订单支付、额度到账、平台 Key 管理、真实调用、usage 查询和异常排查。供应商平台擅长提供模型，通用交易系统擅长处理订单，但套餐额度与真实模型消费、Agent 与实时业务数据之间仍需要一层业务系统连接。

我做这个项目，是为了把三个常被拆开的工程问题放进同一条可验证链路：高并发套餐交易和最终一致性、统一模型接入和额度结算、基于真实业务数据的多 Agent 助手。这样项目既有 Redis Lua、Stream、RocketMQ、缓存一致性等 Java 后端深度，也有 API 网关计费和 Agent 工具权限边界，不是简单 CRUD 或聊天 Demo。

### Q42：项目网关做了什么，为什么需要该网关？

回答：网关对下提供 OpenAI 兼容的 `/v1/chat/completions`，对上调用百炼等兼容供应商，并集中完成以下工作：

1. 用平台模型别名映射数据库模型和供应商模型 ID，客户端不依赖供应商命名；
2. 支持登录会话和 `mh_` 平台 API Key，供应商 Key 只存在服务端；
3. 校验请求大小、消息格式、`max_tokens`、上下文预算，并执行每分钟限流；
4. 使用 Idempotency-Key 防止同一业务请求被重复发送和重复结算；
5. 调用前按输入保守估算和最大输出预算预留额度，上游成功后按真实 usage 结算，明确失败时释放预留，结果不确定时保留待对账状态；
6. 统一响应模型别名、错误语义，并记录 Token、成本、供应商请求 ID 和调用状态。

如果浏览器直接调用供应商，会暴露上游 Key，供应商差异会扩散到客户端，平台也无法统一做租户鉴权、限流、额度扣减、幂等和审计。网关的核心作用是建立一个可信的调用与结算边界，让购买的 Token 额度能够真实约束模型消费，并为以后增加多供应商路由、熔断和对账留出统一入口。

### Q43：Agent 的降级逻辑是什么，什么时候使用 GeneralAgent？

回答：GeneralAgent 首先承接问候、反馈、普通查询、低置信度 `OTHER` 和没有专属映射的长尾问题。已路由到专属 Agent 后，如果目标实例不可用，或者专属 Agent 在**不要求实时权威证据**的路径中执行失败，也可以降级到 GeneralAgent；系统会注入“工具不可用”的降级上下文并清空工具策略，要求它只能给通用解释和下一步建议，不能声称已核验当前状态。

但当前价格、库存、订单、余额和平台规则属于强证据场景。如果所需工具没有启用、预算不足或权威调用失败，系统不会让 GeneralAgent 猜，而是返回“当前无法核验”；交易、账号和风控问题还会标记平台侧复核。也就是说，GeneralAgent 提高的是非实时问答的可用性，不能绕过真实数据门禁。

### Q44：为什么把 Agent 设计成这几类？

回答：拆分标准是业务职责、事实来源、工具权限和失败风险，而不是为了追求 Agent 数量。

- 模型顾问负责模型发现与比较，价格和参数必须来自实时模型目录；
- 成本优化负责 Token 与费用公式，需要固定单位换算、假设和确定性计算；
- 套餐订单负责库存、订单、支付和额度解释，私有数据由 API 按登录身份预取，模型不能自由填写用户 Token；
- API 支持负责 Key、SDK、请求参数和错误码，重点是可执行排查与密钥安全；
- 风控/人工复核负责刷购、盗用和申诉，只能给风险线索，不能自动做封禁、退款或归属结论；
- GeneralAgent 负责普通长尾和受限降级，默认权限最小。

拆开后每类 Agent 可以绑定更短的 system prompt、专属 Skill、最小工具白名单和独立评测集，减少无关工具暴露与规则冲突。代价是路由、并行成本和结果冲突，因此项目只在复合问题中并行，并对工具预算进行切分；生产上仍需要用离线评测和线上指标证明多 Agent 拆分确实优于单 Agent。

## 八、面试表达建议

- 回答时先讲业务问题，再讲技术方案，最后讲兜底和不足。比如不要只说“用了 Lua”，要说“为了防止并发超卖和重复下单，我把库存判断和一人一套餐判断放到 Lua 中原子执行”。
- 遇到一致性问题，不要说“完全一致”，应说明正常链路如何通过幂等、状态检查和库存补偿趋向最终一致，也要主动说明当前缺少 Pending 周期恢复、可靠消息补发和定时对账。
- 遇到热点识别问题要说明边界：项目已基于详情访问和支付购买实现近期行为加权、增长率和时间衰减计算，也已经具备可信的网关调用流水，但调用成功事件尚未接入热度公式，且没有动态 TopN 自动预热。
- 遇到性能问题时，不要编造指标。可以说“理论上减少了 MySQL 直接写压力，实际效果需要结合 JMeter 压测和监控数据验证”。
- 面试官追问缺陷时，可以主动提死信队列、补偿任务、唯一约束、监控告警和压测，这是加分点。

## 九、可以继续完善后再写进简历的点
